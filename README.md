# SC Extranet Tools

Browser-side tooling for the strip-curtains order extranet, built from one repo into two
installed userscripts. It replaces the 26 separate Tampermonkey scripts kept in `legacy/`.

| Bundle | Runs on | Replaces |
|---|---|---|
| `sc-extranet.user.js` | `extranet.strip-curtains.com` | 24 of the legacy scripts |
| `sc-gmail-bridge.user.js` | Gmail, plus the extranet `verify_2fa` page | Gmail Quote Search, Extranet 2FA |

## Install (once per machine)

Tampermonkey cannot authenticate to GitHub, so it never fetches from this repo. It loads
the built file straight off your disk instead.

1. Clone the repo somewhere stable, e.g. `C:\dev\sc-extranet-tools`.
2. `npm install`
3. `npm run build`
4. Chrome or Edge → Extensions → Tampermonkey → **Details** → turn on
   **Allow access to file URLs**.
5. Open `dist/sc-extranet.stub.user.js` and paste it into a new Tampermonkey script.
   Repeat for `dist/sc-gmail-bridge.stub.user.js`. The stubs are generated by the build and
   already contain the correct `@match`, `@grant` and the `@require` pointing at your clone.

Firefox is not supported: it rejects `file://` in `@require`.

## Day to day

```bash
git pull
npm run build      # or: npm run watch
```

Reload the extranet tab and the new code is live. You only reinstall a stub when its
`meta/*.json` changes — a new grant or match, not new code.

If an edit does not show up, set Tampermonkey → Settings → **Externals** → update interval
to *Always*.

## Repo layout

```
meta/          one JSON file per bundle: name, version, match, grant, connect
build.mjs      esbuild; emits dist/<bundle>.user.js and the matching install stub
src/core/      the runtime handed to every module as `ctx`
src/modules/   one folder per feature
src/bundles/   the two entry points
legacy/        the original 26 scripts, kept until every module is verified against them
docs/          the consolidation plan and reference copies of the site's own JS/CSS
```

## Writing a module

A module is a plain object. It declares when to run and where, and receives `ctx`:

```js
import css from './styles.css';

export default {
  id: 'orders.tracking-panel',
  title: 'Tracking panel layout',
  runAt: 'idle',              // 'start' | 'end' | 'idle'
  pages: ['orders-view'],     // [] or omitted means every page in the bundle's scope
  enabledByDefault: true,
  init(ctx) {
    ctx.style.add(css, { id: 'tracking-panel' });
    ctx.observe.each('#Packages-Block', (block) => layout(block));
  },
};
```

Then add it to `src/modules/index.js`.

### Rules

- **No new `window.*` globals.** Modules talk through `ctx` and `ctx.events`.
- **No module builds its own `MutationObserver`** or patches `fetch`/`XMLHttpRequest`.
  Use `ctx.observe` and `ctx.net`; that is why they exist.
- **CSS lives in a `.css` file** beside the module and is imported as text.
- **Existing storage keys are preserved.** Read them through `ctx.settings.raw` /
  `ctx.settings.json`; rename only via `ctx.settings.migrate`.
- **Automation stays gated.** Anything that clicks Save, sends a PO or submits a 2FA code
  keeps its explicit arm step and its legacy default.

### What `ctx` gives you

| | |
|---|---|
| `ctx.page` | `.id`, `.recordId`, `.is('orders-view')`, `.isExcluded`, `.url()` |
| `ctx.observe` | `.each(sel, cb)`, `.onChange(cb)`, `.ready(sel)`, `.silently(fn)` |
| `ctx.route` | `.onChange(cb)`, `.signal()` — SPA navigation, mirrored as `tm:route` |
| `ctx.net` | `.onResponse(cb)`, `.dedupe(match)`, `.request(url, opts)` |
| `ctx.style` | `.add(css)`, `.addToShadow(root, css)` |
| `ctx.settings` | `.raw`, `.json`, `.shared`, `.isEnabled(id)`, `.migrate(from, to)` |
| `ctx.theme` | `.current()`, `.isDark()`, `.set()`, `.toggle()`, `.onChange(cb)` |
| `ctx.events` | `.on(name, cb)`, `.emit(name, detail)` |
| `ctx.dom` | `$`, `$$`, `norm`, `toNum`, `esc`, `el`, `debounce`, `throttle`, `copyText`, … |
| `ctx.log` | `.info`, `.warn`, `.error`, `.guard(fn)` — already scoped to your module id |

## Checks

```bash
npm run check     # lint, build, then verify grants/matches against the built bundle
```

`check:headers` fails if a bundle uses a `GM_*` API it did not declare, declares one it
never uses, or asks for an over-broad match or `@connect *`.
